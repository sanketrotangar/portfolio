Knowledge Base + Assistant

Multi-tenant company knowledge base with a permission-aware agent. Cites every answer, refuses what you are not cleared to see, and flags when documents disagree.

Role
Solo build, end to end: tenant-aware schema, access model, ingestion and retrieval pipeline, agent layer, and the evaluation harness.
Status
In build (Phase 1)
Stack
PostgreSQL + pgvectorRow-Level SecurityHybrid search (RRF) + rerankerSwitchable LLM layerFastAPINext.js

Problem

Company knowledge sits in drives and chats in five versions, and leadership needs the right document at the right moment. Generic RAG chatbots answer from whatever they can see, which means they eventually leak the wrong document to the wrong person.

What I built

How the system runs end to end.

  • Ingest: PDF, DOCX and Markdown are parsed, chunked, embedded, and stored as versioned documents with tenant, department and clearance metadata.
  • Retrieve: vector + keyword search fused with RRF, then reranked. Access is enforced in Postgres via Row-Level Security before the model sees anything.
  • Answer: the agent responds from permitted chunks only, with citations (file, version, date).
  • Deny gracefully: if a restricted document matches, the user is told one exists and can request access. No title, snippet or content is revealed. Requests are logged for document owners.

Key decisions and trade-offs

What I chose, what I rejected, and why.

Choice

Authorization lives in the data layer, not the prompt.

Why: The model only receives chunks the user is cleared for. Prompt-based guardrails fail under adversarial input, and row-level policies do not.

Rejected: Prompt-based guardrails (fail under adversarial injection)

Choice

Two-query retrieval.

Why: One query runs as the user. A second privileged query returns only an existence flag. The extra latency is a deliberate price for being transparent without leaking.

Rejected: Single query without existence visibility, or a leaky unified query

Choice

One Postgres instead of a separate vector database.

Why: Permissions, versions and vectors stay in one transactional store. This fits the target scale. It is not a claim that it beats dedicated vector databases at massive scale.

Rejected: A separate dedicated vector database

Choice

Version-aware answers.

Why: Superseded versions are archived and excluded by default. When two documents conflict, the answer flags the conflict and shows both dates instead of silently picking one.

Rejected: Silent arbitrary document selection

Choice

Multi-tenant from day one.

Why: tenant_id and RLS are on every table, even when running a single tenant. Retrofitting isolation later means rewriting every query.

Rejected: Single-tenant schema with a planned future migration
