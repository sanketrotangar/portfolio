1. Problem

Company knowledge sits in drives and chats in five versions, and leadership needs the right document at the right moment. Generic RAG chatbots answer from whatever they can see, which means they eventually leak the wrong document to the wrong person.

How it works

  • Ingest: PDF, DOCX and Markdown are parsed, chunked, embedded, and stored as versioned documents with tenant, department and clearance metadata.
  • Retrieve: vector + keyword search fused with RRF, then reranked. Access is enforced in Postgres via Row-Level Security before the model sees anything.
  • Answer: the agent responds from permitted chunks only, with citations (file, version, date).
  • Deny gracefully: if a restricted document matches, the user is told one exists and can request access. No title, snippet or content is revealed. Requests are logged for document owners.

3. Key decisions & trade-offs

Deliberate engineering choices, underlying reasons, and rejected alternatives.

Decision

Authorization lives in the data layer, not the prompt.

Why: The model only receives chunks the user is cleared for. Prompt-based guardrails fail under adversarial input, and row-level policies don't.
Rejected alternative: Prompt-based guardrails (fail under adversarial injection)
Decision

Two-query retrieval.

Why: One query runs as the user. A second privileged query returns only an existence flag. The extra latency is a deliberate price for being transparent without leaking.
Rejected alternative: Single query without existence visibility, or leaky unified query
Decision

One Postgres instead of a separate vector DB.

Why: Permissions, versions and vectors stay in one transactional store. This fits the target scale. It isn't a claim that it beats dedicated vector databases at massive scale.
Rejected alternative: Separate dedicated vector database
Decision

Version-aware answers.

Why: Superseded versions are archived and excluded by default. When two different documents conflict, the answer flags the conflict and shows both dates instead of silently picking one.
Rejected alternative: Silent arbitrary document selection
Decision

Multi-tenant from day one.

Why: tenant_id and RLS are on every table, even when running a single tenant. Retrofitting isolation later means rewriting every query.
Rejected alternative: Single-tenant schema with planned future migration

What sets it apart

  • Permission-leak red-team suite: adversarial prompts run as unauthorized users; the pass condition is zero leakage.
  • Access-request workflow: a denied search becomes an approval request instead of a dead end.
  • Executive brief mode: 'prep me for the vendor meeting' produces a cited digest across only the documents that person can access. (Phase 2)
  • Onboarding paths: role-based reading sequences for new hires. (Phase 3)
